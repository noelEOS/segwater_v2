# v3 lineage campaign drivers (2026-09-06 → 08)

The scripts that actually ran the dataset_v3 evaluation and stage-2 campaigns,
copied **verbatim** off the two VMs. Same policy as the parent directory: this is
**a record of what was run, not a library**. Paths are hardcoded, `~` means the
VM's home, and nothing here is parameterised for reuse elsewhere.

⚠️ **Where a name also exists in `../../analysis/` or `../../ship/`, that copy is
authoritative** — see the parent `README.md`.

## ⚠️ Read this before writing a new driver

Every script here was written from scratch on a VM, in `~`, untracked, during a
campaign — and then rescued afterwards. That is the third time in six weeks this
directory has had to absorb scripts born outside the checkout.

Two of them were near-misses worth stating plainly:

* `score_sds_v3*.sh` were written from `docs/RUNBOOK_sds_vm_eval.md` without
  checking whether a driver already existed. One did:
  `../run_sds_mhws_raw.sh`. They agree on every flag that touches the numbers —
  but by luck of the runbook being accurate, not because anything was checked.
  The site-required flags could not diverge (`sds_core.SITE_REQUIRED_FLAGS` is
  enforced in code); the threshold grid and the `--reference` /
  `--submission-type` handling are **not** enforced, and that is where a silent
  divergence would have lived.
* The Demak trend was first computed inline in an ad-hoc script when
  `../../analysis/fit_trend_by_arm.py` already implements the canonical spec for
  exactly that estimand. The published v3 numbers were re-run through it
  (identical to 0.1 ha/yr, plus 95 % CIs the ad-hoc version lacked).

**So: before writing a driver for a tool, find the existing callers.**

    grep -rl "<tool name>" scripts/evaluation/vm/campaign_drivers/

## Caveats on these copies

* **`chain_stage2.sh` is NOT the state that ran the whole campaign.** It was
  edited mid-campaign to drop `segformer` (moved to the other VM). The committed
  copy is the post-edit version: `for tok in unetpp deeplab`. As first run it
  read `for tok in segformer unetpp deeplab`.
* **`run_stage2_arch.sh` was byte-identical on both VMs**; the copy here is the
  train-VM one.
* Everything else is byte-identical to what ran (verified by md5 against both
  VMs at collection time, 2026-09-08).
* `pull_memmaps_v3.sh` is the **second** version. A first attempt used
  `--transfers 4`, which does nothing for two large files, and was stopped and
  rewritten with `--multi-thread-streams 16` (~180 → ~540 MB/s). Only the
  rewrite is here.

## Known divergence from the sibling builders

`../../analysis/build_v3_demak_areas.py` (tracked separately, not in this dir)
omits the `A_PRIORI_EXCLUSIONS = {"S1_20250730_105715_127_1_1"}` guard that the
five sibling area builders carry. This is a **deliberate** omission: the v3
series is uniformly frame `76_8_9`, and that scene is dated 2025-07-30, outside
the ≤ 2024-12-31 analysis window, so it is excluded by the window regardless.
Recorded here so the difference is not mistaken for an oversight.

## Environment these assume

    export PATH=$HOME/miniforge3/envs/torch211_cu128_inference/bin:$PATH
    export LD_LIBRARY_PATH=$HOME/miniforge3/envs/torch211_cu128_inference/lib

Stage-2 scripts use `torch211_cu128` instead, and set `ulimit -n 65536` before
launching (a descriptor leak killed an HPO study at trial 29 without it).

⚠️ Both VMs are named `gpu-rtx-west`. Always use the full hostname:
`gpu-rtx-west.us-west1-b.warm-calculus-507202` (eval) and
`gpu-rtx-west.us-west1-b.smooth-grid-508004` (train).
